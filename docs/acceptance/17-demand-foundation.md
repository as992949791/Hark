# Manual demand research foundation

Scope: [issue 18](https://github.com/as992949791/Hark/issues/18), [implementation plan](../specs/cross-platform-discovery-implementation.md), baseline `v0.1.28-discovery-design`. This release implements storage, ownership, exact jobs and accounting seams. Source adapters, profile preparation, extraction and `/app/research` remain on issues 19/20; it does not search the web or produce real demand results.

## Implemented boundary

- Owner-scoped product/topic runs accept a request UUID, total microdollar budget and at most thirty admitted attempts. Three queued/running unexpired runs per owner bound the queue. Topic and new product URLs need no product project; existing matching owned ready profiles are snapshotted without refresh. Creation inserts one exact `demand_research` job, with no create/profile action, ordinary discovery, scheduler kick or backfill.
- Insert-only document/signal contracts keep source text apart from snippets and profile-preparation material. Composite document/run references prevent attaching another run's document. Retrieval, quote/author validation and signal publication are not installed by this foundation.
- All new run budget writes serialize under one short database lock. One run lease fences admission/finish writes. Each attempt needs a finite positive integer upper bound supplied by a trusted future endpoint adapter; the foundation does not establish any live endpoint/model price. Only one outstanding request per run is admitted. Per-run total/count, existing house daily caps, X switch and sub-caps are checked before an injected transport callback. No network is performed while holding the transaction lock.
- Callback success settles the actual cost atomically into the attempt, run and existing data/model ledger. Repeated settlement does not charge twice. Model provider request identity stays on the attempt. X model charges enter the existing X purpose aggregation. Costs attach to the run rather than the cascading project ledger reference; run-level reports include them, existing project-only readers retain their previous scope. Deleting an optional product project or expiring evidence preserves the run charge. Account deletion retains the existing cascading-data policy.
- Callback failure leaves the ceiling reserved and blocks automatic repurchase. A crashed worker's outstanding request becomes uncertain on reclaim. Explicit server-side receipt reconciliation precedes retry; no public reconciliation action exists. Unexpected provider over-ceiling actual charges are retained and the run is blocked. The cap cannot guarantee a provider obeys its promised bound; the foundation never enables an unverified live endpoint.
- Retry resets the same job only after its previous worker finishes; successful documents and charges remain. New jobs have no recurring successor. Run-owned jobs resolve owner separately from project jobs; scheduled requests cannot run them. Both `DEMAND_DISCOVERY_ENABLED` and `DEMAND_LIVE_ENABLED` default off. Even when the foundation handler is explicitly invoked in tests, it records blocked/source-pipeline-not-installed rather than a fabricated success.
- Expired reads redact content before cleanup. Explicit retention deletes documents/signals/themes and profile/input/progress, retaining run/attempt/ledger billing records and uncertain reservations. The ordinary retention handler invokes one bounded 500-run cleanup batch; no scheduler was enabled for acceptance.

Legacy calls retain their preflight daily-cap semantics; they do not participate in the new reservation lock. This version does not promise a new global atomic cap across legacy callers. The later native adapters must still retain their existing pacing/funding controls and verify endpoint ceilings before live admission.

## Checks and limits

A first behavior test failed for the missing demand module before implementation. Initial dedicated-test migration then caught Drizzle placing composite foreign keys before their supporting unique indexes. Reordering those two generated index statements fixed the unpublished migration. Migration, schema constraints and application behavior were subsequently checked on a new throwaway local `_test` database, never the application's data. The throwaway database is removed after verification.

Initial supported full verification passed 999 tests/105 files. Final supported full verification after review corrections passed TypeScript, ESLint, 1002 tests across 105 files and production build on another fresh throwaway test database. The 30 new tests cover topic/new-product ownership, matching/foreign product references, idempotent creation, bounded owner queue, default-off/zero/unknown-budget admission before callbacks, reservation races, exact settlement, timeouts/reconciliation, stale leases, X caps, evidence expiry, durable charges and migration FK/check constraints. Exact-job tests cover dispatch failure, foreign owner, scheduled/disabled admission, duplicate invocations, undrained siblings, truthful foundation stopping and no recurrence. Existing worker/scheduled/recovery/spend/retention suites remain green.

Independent reviews found three P2 concurrency/recovery issues: an extra pooled connection during a locked reservation, a reclaimed job finishing while its run lease remained held, and retry bypassing the owner queue bound. Each regression failed before correction. Spend reads now use the held transaction; the deterministic one-connection subprocess test finishes all house/X data/model variants instead of reaching its five-second kill deadline. Lease contention releases the same unfinished job, and retry uses the same atomic capacity guard as creation. Both source reviewers confirmed resolution with zero remaining material findings.

No live provider, model quality, remote worker deployment, browser/UI or product relevance acceptance was performed. Fixtures exist only in tests; no synthetic run is inserted in the signed-in application. Supported local preview applied migration 0040 and became ready with all paid caps zero, background/scheduled work and both demand gates off. Health/home returned 200 and an unauthenticated leads request redirected (307). Selected existing product/profile version, source lists, settings, channels, mutes, themes and project ledger counts stayed equal across migration; this is not an all-table/activity comparison. All four new application tables contain zero rows, so no test fixture was inserted into the signed-in app. Independent source reviews are recorded in [review](../reviews/demand-foundation.md); archive refs and exact-commit CI follow on issue 18 after execution. The cross-platform feature remains open until source collection and real UI/integration acceptance finish.
